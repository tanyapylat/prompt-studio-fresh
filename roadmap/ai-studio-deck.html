Block 1
The daily driver
A prompt engineer opens the Studio every week because it's the fastest place to work. Not because we told them to.
  • Playground — prompt, dataset, checks, run, results
  • Trace viewer — separate track, already led
Two features. Two owners. Today we're talking about the first.
Read this as if it already shipped
Run any prompt against 20 real cases and see exactly what broke.
No project. No eval config. No YAML. No final-config flag.
Now tell me what's wrong with it.
What you'd see
  1. Open a prompt from the library. Read-only.
  2. Paste 20 rows of test data. Or drop a CSV.
  3. Add two checks: under 60 characters, never mentions price.
  4. Hit Run.
  5. 14 pass, 6 fail. Failures sorted to the top.
  6. Click a failure. Full output, which check broke, why.
That's error analysis. Ninety seconds instead of an afternoon.
Scope fence

In v1

  • Open any prompt from PS, read-only
  • Paste rows or import a CSV
  • Deterministic checks
  • Run across every row
  • Pass/fail table, failures first
  • Read any full output

Not in v1

  • Saving a version
  • Comparing two prompts
  • Publishing or approving
  • Reusable check libraries
  • LLM judge tuning
  • Traces
The one thing that could sink it
The pitch is speed. The runner is a queue.
  • PS runs evals through Jenkins: In Queue, In Progress, poll every 15 seconds
  • If that's the only path, "hit Run and read the table" becomes "come back later"
Spike it first: can we execute a run synchronously, or do we need a fast path alongside the queue? Every estimate before that answer is a guess.
Leave the room with
  1. Disposable, or does v1 need to save anything?
  2. Deterministic checks only, or LLM judge too?
  3. Who are the 3 people who'd use this weekly? Names, not roles.
  • The queue spike, booked and owned
  • The traces hand-off agreed — flagged trace becomes rows in here
Not today: spec authoring, approvals, migration dates. All real, all later, all more fun to argue about than what we need.
