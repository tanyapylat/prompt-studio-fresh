# Under the Hood: Technical Context, in One Page

This is **not** a technical spec, and it doesn't repeat anything from the workflow docs or the [glossary](07-glossary.md). It's the handful of engineering facts that explain *why* certain business rules in this playbook work the way they do, and where the design is genuinely proven vs. still a plan. Optional reading — the workflow docs stand on their own without it.

## Why "locking in" and reviews can actually be trusted

- **A "locked-in" version is a single atomic transaction, not a save button.** The brief, prompt, checks, test set, and grading rules freeze together in one database transaction — there is no half-frozen state to accidentally review or ship. That's a system guarantee, not a process rule someone has to remember to follow.
- **"Official run" vs. "trial run" is a computed fact, not a label someone assigns.** A run only counts as official evidence if every single piece behind it (brief, prompt, checks, test set) was already locked in at the moment it ran. A trial against anything still in-progress is automatically excluded from ever counting as evidence — the system can't be talked into treating a draft run as proof.
- **The toolbox of checks is a real, already-existing library** (the industry-standard `promptfoo` assertions engine), not a hypothetical list — contains/excludes text, regex, valid JSON, JSON-schema shape, number-in-range, "was the right tool called." Drafting a check means picking and filling in one of these first, before anything gets freshly written.
- **A freshly-written custom check is literally code that runs on shared infrastructure with real system permissions.** That's the concrete reason "always flagged for a human during review, never trusted silently" (04, Roles doc) is a security control, not extra caution for its own sake.
- **Side-by-side comparisons are a native capability, not a bolted-on "compare" feature.** The underlying run structure explicitly supports pinning more than one prompt version at once and fans a single launch into parallel results automatically — that's why every update path in this playbook defaults to "run old and new together" instead of two separate steps someone could forget to do.

## What's live today vs. what's still being built

- **Automatic, always-on production monitoring ("Online Evaluation") doesn't exist yet — it's a planned next phase, not shipped.** Everywhere this playbook says "keep watching after launch," today that means periodically pulling in and reviewing batches of real usage or exported reports by hand — the same checks and bar, just manually sourced for now instead of a live feed. Worth knowing so reviewers don't assume a fully automatic safety net is already running.
- **Rollout has no big-bang migration and no forced cutover.** Existing prompts keep working exactly as they do today, untouched, until someone deliberately brings a specific one into this new process — typically the first time it needs an actual update. The two ways of working simply coexist for as long as needed; nothing breaks or auto-converts in the background.
- **Versioning everything, forever, was checked against real numbers and is cheap.** The brief/prompt/checks/test-set side of this stays small (hundreds to low-thousands of records total, org-wide) no matter how often things fork. The only data that grows fast is actual run results, and that already has automatic cleanup (cleared after 30 days) built into the platform — so "a new version for every edit" isn't a storage or performance concern.
- **Privacy scrubbing reuses an existing, already-in-production redaction service** — the same one already used for today's live evaluations — applied automatically before anything is written permanently. It's an existing mechanism being pointed at a new use case, not new privacy machinery being built from scratch.
