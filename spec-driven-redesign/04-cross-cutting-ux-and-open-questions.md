# Cross-Cutting UX Principles, What Changes vs. Today, and Open Questions

## UX principles (the "feels better than a form, like PromptLayer/LangSmith" bar)

- **One workspace, five panes, no forced navigation.** Spec, Prompt, Eval (Assertions + Judge), Dataset, and Results should be reachable from a single screen with lightweight tab/pane switching — not separate routes like today's `/editor` vs. `/evaluation/:projectId/:versionId`. Every pane is directly editable in place.
- **The Results pane is an annotation tool, not a report.** Per current field practice ([05](05-eval-methodology-best-practices.md)), the highest-leverage investment in the whole product is a good error-analysis workspace: structured filters (pass/fail, assertion type, Spec-criterion coverage, failure cluster, cost/latency outliers) and roll-up summaries (pass rate by criterion, top failure clusters, trend vs. last run) so a reviewer can see what's broken before drilling in; render each output the way a domain expert actually reads it (an email as an email, code with syntax highlighting), keep full trace context available but collapsed by default, support free-text open-coding notes before any category exists, show a bounded progress indicator and keyboard shortcuts for fast review, and prioritize items already flagged by a failing assertion, a low-confidence judge score, or negative feedback — while still mixing in random samples so blind spots stay visible. Every finding should be one click from becoming a concrete, LLM-drafted/human-confirmed change to an Assertion, Dataset row, Spec criterion, or the prompt itself — see [02](02-workflow-starting-anew.md) step 3b.
- **Draft-first, cheap iteration.** Every edit creates a new draft version of just the thing that changed, but a draft `SuiteVersion` stays **re-pinnable** — the same Suite gets re-launched over and over as the author tweaks prompt/assertions/dataset, instead of new Suite ceremony on every tweak. Iteration should feel like autosave-and-rerun, not save-and-navigate.
- **One atomic Publish, not a checklist.** Today's approval flow tracks three independent, looseley-connected signals (final config flag, executed flag, relevancy score) that can drift out of sync. The new model has exactly one frozen, self-consistent, reproducible graph, with one confirmation dialog that lists everything about to freeze.
- **A coverage checklist, always visible, not just at generation.** Next to the Spec, show every success criterion/guardrail with a live yes/no: is an Assertion currently covering it? This is the actual safety net for direct prompt edits — see [02](02-workflow-starting-anew.md) step 4 — since re-running the Eval only catches what it actually checks.
- **Provenance breadcrumbs everywhere.** "This assertion came from spec criterion #3." "This dataset row was added because of a Case C fix." "This run compares v4 against the current published v3." Traceability should be a first-class, always-visible UI affordance, not something you reconstruct from memory.
- **Libraries as real browse surfaces, per spec.** The Eval Service SDD (PR-3/SR-8) specifies this precisely, not just as "a filtered view": every component (Eval, Dataset, Assertion, Judge Policy) carries **private (personal) vs. public (org-wide) scoping with per-component visibility/ownership controls** — not one flat shared library. Discovery needs **structured filtering** (type, owner, tags, creation date, usage count, associated prompt/project), **grouping** (by team, project, judge type, dataset domain), and **semantic search over judge rubrics and dataset descriptions** (not keyword-only — finding "something like a tone check" without knowing its exact name). "Save to library" is a visibility/tagging moment (promote private → public) plus enough metadata (description, tags, owner, version history, usage stats) to make reuse practical at scale, not a new backend concept.
- **Comparison is native, not a side tool.** Multi-target Suites replace the standalone `/compare` page as the default way to validate a new prompt version — see [03](03-workflow-new-version-from-existing.md).
- **Online eval is one click away, not a separate setup — once it exists.** Binding an already-approved `EvalVersion` to production traces should be exposed right next to the Approve/Release actions, since it's the same entity, just a different `RunGroupType`. **Phasing note:** the Eval Service SDD marks online evaluation as **Phase 2, with no executor built yet** — this is a v-next capability, not part of the v1 build. Until then, the equivalent feedback loop runs through **ingested** results (imported Jenkins/PromptFoo reports, or manually reviewed trace exports) rather than a live binding — see [03](03-workflow-new-version-from-existing.md) Case C.
- **Review is a pull request, not a button.** Approval reviews a diffed changeset (Spec, Prompt, Assertions, Dataset, Judge, plus the citable run and baseline comparison) with threaded comments anchored to specific artifacts, an AI review agent posting a first-pass review (consistency gaps, uncovered criteria, regressions — comments only, never the approval itself), and Approve / Request-changes verdicts that persist on the version history. See [02](02-workflow-starting-anew.md) step 8.

## Libraries need a path in from real data, not just a path out to reuse

**Current-state baseline, to be precise about what's actually being proposed here:** today there is no Assertion library, Dataset library, or Judge Policy library at all — `ConfigurationJson` is an opaque per-version PromptFoo blob (see [README](README.md)), not a reusable, independently-versioned entity. The only library that exists today is the Prompt Library, and it has no semantic search — discovery is name/browse only. So everything below, not just the real-data path, is new. Within *this proposal*, the "Save to library" step ([02](02-workflow-starting-anew.md) step 5) and the "Libraries as real browse surfaces" principle above already specify the *reuse* side reasonably well: once an Assertion, Judge Policy, or Dataset exists as one of these new entities, it's designed to be a first-class, versioned thing you can tag, promote to org-wide visibility, and pin into a different Spec later, with real (not just name-match) search. What's the least specified so far, even within this proposal, is the *build* side specifically for real data — the two paths into a Dataset described elsewhere in this proposal are synthetic generation at dry-run time (from the Spec's own examples, see [05](05-eval-methodology-best-practices.md)) and one-row-at-a-time promotion from an error-analysis finding (Case C in [03](03-workflow-new-version-from-existing.md)). Neither is "go get a batch of real interactions and turn them into a dataset" — that needs to be its own first-class workflow, not just a side effect of reacting to a flagged failure.

Concretely, this means:

- **A real-data browse surface, independent of any specific run or finding.** A filterable view over actual production interactions (by time range, by Prompt/Target, by pass/fail if something happened to grade it, by tag) that a user can open proactively at any time — not only after Case C's "a failure cluster was found" trigger. This is the same underlying data Online Evaluation samples from (or, pre-Phase-2, the same ingested batch/trace exports), just exposed as its own browsable surface rather than only surfacing one row at a time inside an error-analysis note.
- **Bulk selection into a Dataset, not just single-row promotion.** Select any number of real interactions from that browse surface and one action ("Add to Dataset") turns them into `DatasetItem` rows in a new or existing draft `DatasetVersion` — building a dataset from fifty real support tickets should be one action, not fifty individual "promote this row" clicks.
- **The same PII redaction gate applies uniformly**, regardless of whether a row arrives via bulk import from this browse surface or via one-off promotion from error analysis — a Dataset row never expires the way a Run payload does, so nothing raw gets in without passing through redaction first (same gate already noted in [03](03-workflow-new-version-from-existing.md) Case C).
- **The same "build from real data" capability applies to Assertions and Judge Policies, not just Datasets.** A real interaction is also the natural seed for "this specific case should always pass this check" (a candidate Assertion, LLM-drafted from the example, human-confirmed) or for a Judge Policy's calibration sample (see [05](05-eval-methodology-best-practices.md)'s calibration loop) — browse-and-select-from-real-data is one shared capability across all three artifact types, not a Dataset-only feature.
- **Once built this way, nothing further is needed for reuse.** A dataset assembled from real data goes through the exact same "Save to library" action as a synthetic one, with the same visibility/tagging/versioning. The gap this closes is entirely on the "how do you get real data in" side — the reuse mechanics in [02](02-workflow-starting-anew.md) step 5 and the Library UX principle above already work for any Dataset/Assertion/Judge Policy regardless of how it was built.

This deserves a first-class entry point in the workspace — a **"Build from real data"** action sitting right next to **"Generate"** on the Dataset, Assertion, and Judge Policy panes — not something a user has to discover through the error-analysis flow.

## Positioning: system of record and library, not a personal playground

A key deliberate difference from tools like LangSmith: LangSmith's model is **account/workspace-scoped** — prompts, datasets, evaluators, and experiments live inside a personal or team workspace, organized around *that account's usage*. Prompt Studio (working title — or **"Spec Studio"**, which honestly fits the new center of gravity better) should instead be the **organization-wide source of truth, library, and overview of all these artifacts**:

- One shared, permissioned catalog of Specs, Prompts, Evals, Datasets, and Judge Policies across the whole org — the same access model the Prompt Library has today (per-project Read/Full, public/private), extended to the new artifact types, not siloed per-user workspaces.
- The **home surface is an overview**, not a playground: what exists, who owns it, what state it's in (draft/published/deprecated), what's linked to what (lineage), and what's running against production right now. Playground-style iteration happens *inside* an artifact's workspace; discovery and governance happen at the library level.
- Reuse is the point: another team should find and pin your published "no PII in output" assertion or "golden support tickets" dataset from the shared library, not rebuild it inside their own workspace. This is exactly what the Evals Platform's client-scoped, first-class entities enable — the UI just has to make the library the front door rather than an afterthought.

## Concrete UX patterns worth borrowing from LangSmith (screens reviewed 2026-07-29)

From the screenshots shared during review — LangSmith has no Spec concept, but several of its prompt/eval development patterns are directly applicable:

- **Playground with inline examples table.** Prompt editor (with `{{variable}}` placeholders and a Mustache-style syntax) sitting directly above a small table of examples (inputs + reference outputs), with "New Experiment — 3 examples" one click away. This is the right feel for our Prompt + Dataset panes: the test rows live *with* the prompt while iterating, not on another route. Maps cleanly to a draft `DatasetVersion` pinned in the same draft Suite.
- **The judge is an editable prompt with a live test harness beside it.** Their evaluator editor shows the full LLM-as-judge rubric prompt (pass/fail definitions, instructions, reminders — not a hidden black box) with a right-hand panel that maps a real dataset example (INPUT / OUTPUT / REFERENCE OUTPUT) through the judge and shows the Result immediately. This is exactly the UX our `JudgePolicyVersion` editor needs, and it's the natural surface for the **judge-calibration loop** from [05](05-eval-methodology-best-practices.md): label a few examples, run the judge against them right there, watch agreement build. (Calibration here is a recommended practice a user can run whenever they want more confidence in a judge, not a required gate before publishing — see [02](02-workflow-starting-anew.md) step 6.)
- **Structured judge output config ("Feedback configuration").** Their evaluator returns a named, typed verdict (e.g. boolean `assertions_passed`) with an optional "include reasoning" toggle — mirroring our `Score.Passed` + `Score.Reason` split. Making the judge's output contract explicit and binary in the UI reinforces the binary-verdict practice from [05](05-eval-methodology-best-practices.md).
- **Two creation paths: LLM-as-a-Judge vs. Code Evaluator.** Their "create from scratch" screen offers exactly our two assertion tiers (`rubric_grading` vs. `code_assertion`) as equal, visible choices. Worth copying — with our addition that the product *recommends* the cheaper tier per criterion rather than presenting them neutrally.
- **Pre-built evaluator catalog — borrow the shelf, curate the contents.** LangSmith ships categorized templates: Security (PII Leakage, Prompt Injection, Code Injection), Safety (Toxicity, Bias & Fairness), Quality (Hallucination, Correctness, Assertions, Conciseness). The *shelf* UX is right for our Eval Library. But per [05](05-eval-methodology-best-practices.md), seed it with the **mechanism-level** checks (the Security/Safety column — PII, injection, toxicity are well-defined and reusable) and be deliberately skeptical of the generic **Quality** tier ("Conciseness," "Correctness" as one-size-fits-all judges) — those are exactly the off-the-shelf metrics Hamel warns create false confidence. If they exist in our library at all, label them as exploration aids, not release gates.
- **Datasets & Experiments as a flat, first-class list.** Name, description, example count, experiment count, last-experiment timestamp — a simple sortable catalog view. Same pattern for our Dataset Library, with two additions theirs lacks: **version/lifecycle status** (draft/published/deprecated) and **provenance** (which Spec/run generated it).

## What this replaces from today's system

| Today | Proposed |
|---|---|
| `PromptRequirement` (statement + criterion, drives assertions only) | `Spec` (full brief: goal, contracts, guardrails, criteria, examples), drives prompt + assertions + dataset together |
| `ConfigurationJson` — one opaque PromptFoo YAML blob per eval config | Normalized, reusable `Assertion` / `Dataset` / `JudgePolicy` / `Eval` entities, each independently versioned |
| Manual dataset authoring (CSV upload or hand-typed rows) as the main path | Dataset seeded from Spec examples/edge cases at dry-run time, still manually editable afterward, **or built in bulk directly from real production data via the Library's browse surface** (see "Libraries need a path in from real data" above) |
| Eval relevancy score (LLM-as-judge, no threshold, easy to game by "already > 0 skips recalculation") | Dropped as a gate — replaced by an actual **citable pass rate** from a real run against the frozen bundle |
| Three independent approval checks (Final Config / Successful Test Case / Executed) | One atomic publish + one auto-triggered citable run as evidence |
| `/compare` page, informal, disconnected from approval | Multi-target Suite comparison, native to the same run that can gate publish |
| "Compare & Approve" — a diff viewer plus an Approve button, no way to discuss | PR-style review: threaded comments anchored to spec criteria / prompt lines / assertions / dataset rows, AI review agent as first-pass reviewer, Approve / Request-changes verdicts kept in version history |
| Online eval as a separate, later-bolted-on feature | Online eval as the natural continuation of the same `EvalVersion` used to gate release |
| "Build Prompt/Eval with Agent" — external deep link to a separate meta-prompting chat | In-product Spec-to-bundle generation ("dry run"), with the option to still use a conversational assistant to *draft the Spec itself* |

## Open questions (need your call)

These are the decisions that materially shape the workflow and aren't fully resolved by the data model or current-state docs:

1. **Where does Spec live technically?** As a new Prompt-Studio-owned entity with its own logical/version tables (this doc's recommendation), as an extension of the existing `PromptRequirement` table, or as a new small "Spec Service"? This affects migration effort for existing prompts.
2. ~~**Retrofitting legacy prompts.**~~ **Resolved by the Eval Service SDD** (see [06-sdd-alignment-and-resolutions.md](06-sdd-alignment-and-resolutions.md)): no bulk/automatic migration, and historical run results explicitly do not carry over. All new prompts use the new model from day one; existing prompts stay on the legacy model until someone deliberately migrates that specific one, naturally triggered by their next Case A/B flow. No forced cutover.
3. **Diff-driven regeneration from a Spec fork (Case B):** should proposed deltas (new/changed assertions, new dataset rows, prompt diff) apply automatically as new drafts the user then edits, or should the system only *suggest* them and require an explicit "accept" per item? Automatic-with-easy-undo is faster; suggest-first is safer against silently discarding hand-tuning. **Scoped v1 answer in [06](06-sdd-alignment-and-resolutions.md):** suggest-first, and specifically via semantic search over the existing Assertion library (a capability the SDD already requires for other reasons) to propose "this changed criterion looks like it maps to assertion X" rather than the system claiming to reliably know the mapping.
4. **Approve evidence: always a fresh citable run, or can a matched draft count?** The data model lets a draft launch's `comparability_fingerprint` be matched against what was later published, to show "this exact configuration already ran." Should Approve require a brand-new citable run every time (simple, always fresh), or can a matching prior dry run satisfy the gate directly (faster, but relies on the fingerprint match logic being airtight)? This doc recommends always re-running (simple, cheap since nothing changed) but flags it as a call worth confirming.
5. **Default dataset size/generation depth for a dry run.** How many synthetic rows should a first dry run generate beyond the Spec's own examples — a fixed small number (fast iteration) or scaled to the number of success criteria/edge cases (more coverage, slower first run)?
6. **SkipApprovalGate-equivalent.** Today's `SkipApprovalGate` project tag bypasses all validation. Does an equivalent "fast lane" still need to exist in the new model (e.g., skip the auto-citable-run-and-Approve step for low-stakes internal prompts), or should the new unified gate be cheap/fast enough that nobody needs to skip it? See question 12 below for a scoped, principled alternative (fast-track tier) rather than a blanket bypass tag.
7. ~~**Who can edit a Spec vs. who can edit the generated Prompt/Eval/Dataset independently?**~~ **Resolved for this team's actual structure**, per [05-eval-methodology-best-practices.md](05-eval-methodology-best-practices.md) and [process-playbook/04](../process-playbook/04-roles-responsibilities-and-approvals.md): the Product Manager owns the Spec's content, the pass/fail bar, and final sign-off, but is not the hands-on annotator — this team's Prompt Engineer role already covers prompt strategy *and* writing/running evals, so the Prompt Engineer does the day-to-day error-analysis pass and can edit Prompt/Eval/Dataset independently, escalating to the PM as tie-breaker or when a finding looks like a new requirement rather than a wording fix. This is a variant of Hamel's "benevolent dictator" default (which assumes the domain expert is also the annotator), adapted to a team where those two functions sit in different roles.
8. ~~**How hard should the product enforce "don't generate `rubric_grading` assertions from every Spec criterion by default"?**~~ **Resolved, per [02](02-workflow-starting-anew.md) step 2:** the generator tries the cheapest tier first as a default, not a silent hard rule — map the criterion onto an existing **promptfoo assertion type** first; if nothing fits, the generator writes a small custom check itself, flagged for the AI review agent (step 8 of [02](02-workflow-starting-anew.md)) rather than trusted silently; a check too novel or risky even for that becomes an engineer request; and a criterion that fits none of the code tiers falls back to `rubric_grading`. This keeps the *Eval Service SDD*'s security concern (freeform generated JS as a runner-executed surface) in view without requiring every non-curated check to detour through an engineer.
9. ~~**Where do judge-calibration labels live, and who's expected to produce them?**~~ **Largely moot now that calibration isn't a publish gate** (per [02](02-workflow-starting-anew.md) step 6) — nobody is forced to produce labels on a deadline. The question still matters for whoever *chooses* to calibrate a judge for their own confidence: reuse dry-run/error-analysis annotations already collected as a bootstrap sample, human confirms/corrects rather than labeling from scratch, and reusing an already-calibrated *published* library Judge Policy needs no fresh labels at all. No cap/round limit is needed anymore since nothing blocks on it — calibrate as much or as little as the judge's owner wants.
10. **Review timing: before or after the freeze?** The flow as drafted is Publish (freeze) → citable run → PR-style review → Approve, so "Request changes" forks new draft versions and re-reviews. The alternative is reviewing the *draft* changeset first and making approval the trigger for the atomic publish + citable run — fewer throwaway frozen versions, but the reviewer is then approving something that could still theoretically change between review and freeze (mitigable with the `ComparabilityFingerprint` hash). Version-noise vs. review-integrity trade-off — needs a call.
11. **How far can the AI review agent go?** As drafted it only comments (consistency gaps, uncovered criteria, regressions) and the human approves. Should it also be able to *block* (a hard gate on, say, "criterion with no covering assertion"), or auto-approve trivial changesets (e.g., Case C dataset-row additions that pass everything)? More agent authority = less friction but weakens the human-owns-the-bar principle from [05](05-eval-methodology-best-practices.md).
12. **Should there be a fast-track approval tier?** [06](06-sdd-alignment-and-resolutions.md) proposes: changesets with no regression on the citable run *and* no new/changed `rubric_grading` assertion (prompt-wording-only tweaks, Case-C dataset-only additions) auto-clear with an async notification to the domain expert, instead of blocking on synchronous PR-style review. Anything touching guardrails, criteria, or judges still requires mandatory human review. Is this an acceptable modern replacement for `SkipApprovalGate`, or too permissive?
13. **Semantic spec-conformance check for prompt-only edits.** Case A's safety net today is coverage-complete assertions plus a same-dataset comparison run, which only catches a spec violation if some Assertion happens to test for it (see the added note in [03](03-workflow-new-version-from-existing.md) Case A). Should the AI review agent additionally compare the new prompt content against the Spec text directly, independent of assertion coverage, and should a wording diff automatically propose a small batch of new dataset rows targeted at the changed portion of the prompt before the comparison run, so the check covers input space the old dataset never had reason to test? This is the prompt-only-edit analogue of the diff-driven regeneration already scoped for Case B.

Happy to go deeper on any single step, sketch the actual screen layout for the five-pane workspace, or turn any of these open questions into a proper decision doc — just point me at which one.
