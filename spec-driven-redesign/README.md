# Spec-Driven Prompt Engineering — Redesign Proposal

This is a **brainstorm / recommended-workflow proposal**, not current-state documentation. It reimagines Prompt Studio around three pillars the team is converging on:

1. **Spec-driven prompt engineering** — a structured spec is the source of truth that seeds the prompt, its assertions, and its dataset.
2. **Evals Platform** (formerly referred to as "Eval Service") — assertions, datasets, judges, evals, and suites become reusable, versioned, first-class entities owned by a central service (see `Evals Service- Data Model.md`), instead of opaque PromptFoo YAML blobs per version.
3. **Online evaluations** — the same evals that gate release are reused to continuously grade production traffic.

## Inputs this proposal is grounded in

- **Current-state behavior** — [`../prompt-management-docs/`](../prompt-management-docs/README.md): today's project → version → eval-config → approve → publish lifecycle, roles, and gates.
- **Current-state code** — `ja-PromptManagement` repo (read-only reference, not modified): confirms eval configs are opaque `ConfigurationJson` blobs, `PromptRequirement` is the closest thing to a "spec" today (drives assertions only, not prompts), online evals already treat production traces as ephemeral test cases, and "Build Prompt/Eval with Agent" is an external meta-prompting deep link rather than an in-product generation pipeline.
- **Target-state data model** — `Evals Service- Data Model.md`: Assertion, Target, Dataset, Judge Policy, Eval, Suite, and the Run Group → Run → Run Item → Score execution layer, plus the versioning foundations (logical/version split, draft/published/deprecated lifecycle, one-atomic-publish, citable vs non-citable results).
- **Target-state narrative doc** — `Evals Service SDD.md` (author @Volodymyr Romaniv, team Cyborgs): the actual SDD — four-subsystem architecture, security posture, data volumes, and the resolved/open questions log. Cross-checked against this proposal in [06](06-sdd-alignment-and-resolutions.md).

## One-paragraph summary

A **Spec** is a new, versioned, Prompt-Studio-owned artifact (goal, required input/output contract, guardrails, success criteria, examples/edge cases). Creating or forking a Spec and running **"dry run"** auto-drafts a coherent bundle in the Evals Platform — Assertions (from success criteria/guardrails, defaulting to the cheapest check that plausibly covers each one, mapped onto the existing promptfoo library before any custom code gets generated), a small Dataset (from examples/edge cases, generated via structured dimensions rather than naive prompting), a Judge Policy, an Eval (the bundle + aggregation rule), a Target (wrapping the drafted Prompt version), and a Suite (eval + dataset + target) — then launches it as a non-citable batch run so the user immediately sees whether the draft prompt already satisfies the brief it was built from. Every generated assertion is treated as a **provisional hypothesis**, not a trusted evaluator, until it survives real error analysis in a Results pane built for that (filters, roll-up summaries, and one-click LLM-drafted/human-confirmed promotion of a finding into an Assertion, Dataset row, Spec criterion, or prompt edit) — the dry run gets the bundle runnable fast, but reading actual outputs (and, later, production traces) is what makes the eval *correct*, per current field practice (see [05](05-eval-methodology-best-practices.md)). Every artifact (Spec, Prompt, Assertions, Dataset, Judge, Eval, Suite) stays independently editable and versioned, exactly like today's prompt versions, and can be saved into shared libraries for reuse across other prompts. Publishing is one atomic action that freezes the whole graph and triggers a confirmatory **citable** run — no separate judge-calibration gate sits in front of it, though calibrating a judge against a human-labeled sample remains good optional practice — and that citable run becomes the evidence for a human Approve gate, replacing today's three disconnected approval checks with one unified, richer bundle. Building a new version on top of an old one reuses this same loop, but adds the old prompt's Target into the same Suite as a second target so the new run is automatically a side-by-side regression comparison against the current baseline, not a fresh eval done in isolation. After release, the exact same Eval version can be re-bound directly to production traces as an Online Evaluation, so pre-release and post-release quality are measured with the same bar — and failure patterns discovered there feed straight back into the Dataset, Assertions, and even the Spec itself, which is the main way eval quality actually improves over time.
